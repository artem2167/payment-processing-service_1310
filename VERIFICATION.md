## Покрытие ТЗ

| Требование | Реализация и проверка |
| --- | --- |
| FastAPI, Pydantic 2, SQLAlchemy 2.0 async, PostgreSQL, FastStream/RabbitMQ | `pyproject.toml`, `uv.lock`, асинхронные API, БД, HTTP и worker; реальные интеграционные тесты |
| Поля платежа, Decimal, RUB/USD/EUR, JSON metadata, три статуса, даты | `app/models.py`, `app/schemas.py`, миграция; проверки типов, границ и сохранения данных |
| POST с 202 и обязательным Idempotency-Key | `app/api/payments.py`, `app/services/payments.py`; обычные, повторные и конкурентные запросы |
| GET с подробными данными | Тот же router; успешное чтение, 404 и сохраненная точная сумма |
| Статический X-API-Key для всех endpoint | Общая проверка в `app/main.py`; ключ проверяется до обращения к БД |
| Атомарное создание платежа и outbox | Одна транзакция, уникальный ключ в PostgreSQL; проверка rollback при ошибке записи события |
| Очередь `payments.new`, один consumer | Durable topology, single active consumer, prefetch 1; фактическая очередь и subscriber |
| Эмуляция шлюза 2–5 секунд, 90/10 | `app/services/gateway.py`; управляемые тесты задержки и обеих ветвей результата |
| Сохранение результата перед webhook | `app/messaging/consumer.py`; независимое чтение результата из БД во время HTTP-этапа |
| Уведомление об успехе и бизнес-отказе | Один формат webhook, стабильный `event_id`; бизнес-отказ не меняется при повторах уведомления |
| Outbox с гарантией повторной публикации | `app/messaging/outbox.py`; publisher confirms, mandatory routing, persistent messages, конкурентные relay и восстановление после сбоя |
| Три попытки с экспоненциальной задержкой | Счетчик и новые события сохраняются атомарно; задержки 5/10 секунд, повтор старого сообщения не создает новую попытку |
| DLQ после исчерпания попыток | Событие DLQ записывается транзакционно и публикуется relay; проверена реальная маршрутизация в RabbitMQ |
| ACK после фиксации работы | Manual ACK; при ошибке БД сообщение остается неподтвержденным и возвращается в очередь при восстановлении соединения |
| Alembic, Docker Compose, README | Начальная миграция, четыре основных сервиса, одноразовый migrate, healthchecks, volumes и воспроизводимые команды |

Тесты создают собственные временные схемы и очереди. Демонстрационные сценарии используют новые ключи и платежи; существующие данные не очищаются. Контейнеры отдельного тестового проекта после проверки удалены, рабочий проект оставлен запущенным.

## Воспроизведение

Из корня проекта, после подготовки `.env`:

```powershell
docker compose --profile demo up -d --build --wait
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests tests
docker compose -f compose.test.yaml down
uv run --frozen ruff check app migrations tests examples scripts
uv run --frozen ruff format --check app migrations tests examples scripts
docker compose run --rm migrate alembic check
uv run --frozen python -m scripts.smoke --api http://localhost:18000
uv run --frozen python -m scripts.resilience --api http://localhost:18000
```

На этой машине в `.env` установлен `API_PORT=18000`, поскольку порт 8000 занят другим приложением. Для нового окружения с портом 8000 замените адрес в командах. Приемник доступен на `http://localhost:8080/events`, RabbitMQ Management — на `http://localhost:15672`. API требует ключ из `.env`, включая `/health`.

Локальные журналы последнего прогона находятся в `tmp/tests-validation-fix.log`, `tmp/smoke-validation-fix.log` и `tmp/resilience-validation-fix.log`. Они не нужны для запуска и не включаются в архив исходников.

## Границы гарантий

Используется эмулятор шлюза; реальные списания не выполняются. Три попытки означают три логические попытки обработки. Авария после успешного HTTP-ответа и до фиксации доставки может привести к повторному webhook с тем же `event_id`; получатель должен дедуплицировать его. При постоянно недоступном получателе работа исчерпывается в DLQ. Эти ограничения отражены в README и соответствуют реализованному протоколу доставки.
